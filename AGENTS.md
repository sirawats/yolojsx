# Repository Guidelines

## Product Goal and Priorities

Rtifact is an agent-first, zero-setup Node environment for turning JSX into a
portable, interactive HTML artifact with Vite, Ant Design, Tailwind CSS, React
Icons, and PrismJS.
Technical users need coding agents to turn content, data, and small workflows
into portable, readable, interactive artifacts without the limitations of
Markdown and PDF or the token cost and inconsistency of hand-generated HTML.
The primary authoring workflow is JSX generated by AI agents, with people
focused on the resulting artifact rather than writing or reading its source.
Optimize the CLI, diagnostics, documentation, and conventions for predictable,
token-efficient agent use without making normal human-authored JSX awkward.

The default build produces one portable `.html` file. Its application payload
is gzip-compressed inside the file and restored in the browser, while controlled
runtime dependencies load from exact-version CDN URLs. `--self-contained`
embeds those runtimes for offline use. `--out-dir` instead produces a
conventional deployable `dist/`-style asset directory. All are first-class
contracts; prefer the default single-file workflow when requirements do not
distinguish between them. A portable file should run without neighboring local
assets. Remote runtimes, fonts, images, and application data are allowed, and
agents should consider graceful degradation when a remote resource is
important, but must not bury compact, content-first JSX under exhaustive
fallback code.

Apply product priorities in this order:

1. Reliable, portable artifacts and correct behavior.
2. Agent-first operation, including official skill files for Codex, Claude Code,
   Antigravity, OpenCode, and similar agents.
3. Human comprehension: legible, scannable, well-structured rendered content.
4. Useful interactivity, responsive UX, and accessibility.
5. Consistent visual quality through themes and the supplied frontend stack.
6. Compact, reusable, token-efficient AI-authored JSX.
7. Small artifact size.

“Human-readable” describes the rendered experience, not generated HTML source.
It includes:

- **Legibility:** normally use 16–20px body text, WCAG AA contrast (at least
  4.5:1 for normal text and 3:1 for large text), and comfortable foreground and
  background colors rather than unnecessarily harsh extremes.
- **Readability:** normally keep prose lines around 45–75 characters, line
  height around 1.4–1.6, clear paragraph spacing, and responsive typography.
- **Comprehension:** use semantic HTML, a distinct heading hierarchy, whitespace,
  short paragraphs, lists, callouts, and other chunking that helps readers scan,
  retain, and act on information.

Representative uses include API test reports, internal setup guides, feature
demos, design-choice comparisons, and small development tools such as JWT
decoders. These examples indicate the product's center of gravity; they are not
a whitelist.

Prefer the supplied stack over custom infrastructure: React for structure and
state, Ant Design for interactive components, Tailwind for layout and focused
utility styling, Rtifact themes for visual direction and semantic tokens, React
Icons for interface symbols, and PrismJS for syntax highlighting. Import only
the Prism languages an artifact uses. Reuse these capabilities before writing
custom components or large custom CSS.

Official Rtifact skill files are a product surface, distinct from this
repository's contributor and OpenSpec skills. They should teach agents the
supported stack, theme behavior, CLI and output modes, compatible application
shapes, compact JSX authoring, and rendered readability and interaction best
practices.

## Architecture and Layout

- `src/bin.ts` is the executable source entry point; runtime TypeScript modules
  live in `src/` and compile to the untracked `lib/` package directory.
- `scripts/` contains development and release verification tools.
- Tests use Node's built-in runner and are split between `test/unit/` and
  `test/integration/`; shared fixture helpers live in `test/helpers.ts`.
- `examples/` contains the canonical standalone JSX inputs;
  `skills/rtifact/examples/` is their exact skill-side copy. `website/index.tsx`
  is the project website and imports the example and theme catalogs dynamically.
- Public requirements live in `openspec/specs/`; active change artifacts live in
  `openspec/changes/`; completed records under `openspec/changes/archive/` are
  historical and should not be edited.

## Setup and Commands

- Use `npm ci` for a clean, lockfile-exact install. Use `npm install` only when
  intentionally changing dependencies, and commit the resulting lockfile.
- The published CLI supports Node `^20.19.0 || >=22.12.0`. Repository
  development on the Node 22 line requires `>=22.13.0` because of ESLint 10.
- `npm run dev` starts Vite with hot reload for `website/index.tsx` using
  the built-in `rtifact` theme. Do not start this persistent server automatically; the
  user runs it when needed. To serve a custom entry, run
  `npx tsx scripts/dev.ts <entry> [theme]`; the optional second positional value
  accepts the same preset name or custom theme path resolved by the CLI.
- `npm run cli -- <entry> [options]` runs `src/bin.ts` directly without first
  compiling `lib/`; use it for source-level CLI development.
- `npm run build && node lib/bin.js examples/TaxCalculator.jsx` performs a manual CLI smoke test.
  `--out-dir dist` exercises directory output.
- `npm run test:unit` and `npm run test:integration` run focused test groups;
  `npm test` runs both serially.
- `npm run format` writes Prettier changes; `npm run format:check` only checks.
- `npm run lint` checks ESLint; `npm run lint:fix` applies safe fixes. To fix both,
  run `npm run lint:fix && npm run format`.
- `npm run check` type-checks repository TypeScript.
- `npm run verify:package` packs and extracts the npm artifact, links existing
  dependencies, and exercises all CLI modes without downloading packages.
- `npm run verify` is the required final gate: formatting, linting, tests, syntax,
  package contents, and packaged-artifact verification.
- Dependency or release work also runs `npm audit`, `npm run check:licenses`, and
  `npm run readiness`.

CI runs `npm run verify` on every pull request and on pushes to `master`.
Branch protection requires these checks to pass before merging.
Run it locally before handing work off.

## Code Style

- Prettier and ESLint are authoritative; do not hand-format around them.
- Use native ECMAScript modules and explicit `.js` import extensions.
- Prefer named exports and small modules with one clear responsibility.
- Use `camelCase` for variables/functions, `UPPER_SNAKE_CASE` for constants, and
  descriptive lowercase filenames such as `dependencies.ts`.
- ESLint scopes Node globals to CLI, source, script, config, and test files, and
  browser globals to `examples/**/*.jsx` and `website/**/*.tsx`. Update
  `eslint.config.js` if adding TypeScript outside those locations.

## Implementation Rules

- Trace the real CLI flow and reuse existing helpers before adding code.
- Keep changes focused. Do not add speculative abstractions, configuration, or
  dependencies.
- Prefer standard, maintainable solutions over awkward or impractical
  workarounds.
- Fix shared behavior at its `rtifact` root; do not patch `website/` or an
  example unless the bug is specific to that page.
- Preserve input-project resolution, Vite-config isolation, package aliases,
  theme application, and React/Tailwind/Ant Design integration unless the public
  specification explicitly changes.
- Filesystem safety is a product contract. Preserve staged publication, ownership
  markers, symlink/path validation, failed-build rollback, and input immutability.
- Treat JSX and custom CSS as trusted local code, but keep path and output
  validation at every filesystem boundary.

## Theme and Ant Design Tokens

Built-in definitions from `src/themes/*.jsx` and custom modules selected through
`resolveThemeSelection()` enter `createTheme()`. Global `antDesign.token` values
then pass through the algorithm selected in
`src/templates.ts` → Ant map and alias tokens → default component tokens.
`createAntDesignComponentOverrides()` instead supplies direct component
overrides, which bypass the algorithm unless a component-level algorithm is
enabled. Seed tokens such as `colorPrimary` are algorithm inputs, not guaranteed
final colors. Check the installed `antd` version and matching Context7 docs;
inspect `node_modules/antd/es/<component>/style/` and `rg` token consumers when
behavior depends on Ant's internal mapping.

Choose the narrowest token layer:

- preset semantic values define the palette and semantic relationships;
- `antDesign.token` defines shared Ant Seed/Alias Tokens;
- `antDesign.components.<Component>` defines component-specific structure or
  state;
- application classes/CSS define application-specific styling, not built-in
  theme behavior.

`OVERRIDDEN_ANT_DESIGN_COMPONENT_NAMES` lists intentional overrides; it is not
the Ant component catalog. Do not copy upstream defaults or add components
speculatively. Remove redundant overrides, use installed-version official token
names, and keep runtime token values serializable primitives.

Validate final colors against their actual canvas/container/elevated
surface/rail, compositing alpha first. Require 4.5:1 for normal text and 3:1 for
large text, controls, focus, and selected indicators; enabled and disabled
states must remain distinct. Check both `colors.surface` and
`colors.surfaceRaised`.

Protect catalog-wide constraints in `validateThemeCatalog()` and token mappings
with focused unit tests. Validate representative light and dark presets and
inspect rendered output when relevant. For public changes update the theme spec
and changelog, mirror edited examples into the skill, and run `npm run verify`.

On Ant upgrades, recheck overridden token names, `prepareComponentToken`
mappings, contrast constraints, and representative rendered components.

## Website and Examples

- The website derives examples with `import.meta.glob("../examples/*.jsx")` and
  themes from `THEMES`; do not duplicate either catalog manually.
- `src/themes/rtifact.jsx` is the website shell's built-in brand theme. Apply it through the
  existing Rtifact build boundary, which generates the semantic CSS and outer
  Ant Design provider. Do not import it into `website/index.tsx`, inject another
  theme stylesheet, or add a nested page-level `ConfigProvider`.
- Keep the website theme selection synchronized in the `npm run dev` script and
  both GitHub Actions website builds. The production-style command is
  `npm run build && node lib/bin.js website/index.tsx --out-dir dist --theme rtifact`.
  The showcase preview remains independent and must continue applying the
  visitor-selected built-in theme inside its iframe.
- After editing `examples/`, copy the whole catalog into the skill with
  `cp -r examples/. skills/rtifact/examples/`. Keep both directories identical;
  remove any skill-side file whose canonical example was deleted.
- Keep showcase controls keyboard accessible and responsive. Test website changes
  with a production-style CLI build in addition to formatting and linting.
- Use `examples/TaxCalculator.jsx` for the smallest smoke test and broader examples only
  when their behavior is relevant.

## Testing and Documentation

- Name tests `*.test.ts` and use `node:test` with `node:assert/strict`.
- Add unit tests for pure parsing, validation, and transformation logic.
- Add integration tests for CLI builds, diagnostics, generated assets,
  filesystem safety, packaging, or other cross-module behavior.
- Register temporary-fixture cleanup with `t.after(...)`. Assertions should test
  behavior, not formatting that Prettier may legitimately change.
- No numeric coverage threshold is enforced; add focused tests that protect the
  changed behavior.
- Update the relevant `openspec/specs/` requirement when public CLI behavior,
  output safety, theme contracts, or package format changes.
- Update README/help examples together, and add an `Unreleased` changelog entry
  for user-visible changes.

Do not commit generated HTML, `dist/`, `lib/`, tarballs, temporary fixtures,
credentials, or unrelated formatting.
